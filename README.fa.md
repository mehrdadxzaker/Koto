کوتو عامل‌های کدنویسی تجاری و متن‌باز را در یک گردش کار کنار هم قرار می‌دهد.
CLI را باز کنید، اشتراک فعلی یا یک مدل محلی اختیاری را انتخاب کنید، پروژه را توضیح
دهید و پیش از شروع کار، برنامهٔ قابل‌ویرایش را بازبینی کنید. عامل‌ها در worktreeهای
مستقل Git کار می‌کنند؛ پیش از ادغام، سهم هرکدام را بازبینی می‌کنید.

**امکانات فعلی:** راه‌اندازی راهنما، ذخیرهٔ انتخاب‌ها و نشست‌ها، کار هم‌زمان روی پروژه،
کنترل ترمینال بومی، ادامهٔ گفت‌وگو در حالت‌های پشتیبانی‌شده و ادغام با تأیید شما.
**کوتو نرم‌افزاری در مرحلهٔ آلفاست.** پذیرش ثبت‌شدهٔ CLI در
[#543](https://github.com/mehrdadxzaker/Koto/issues/543) پیگیری می‌شود؛
[یادداشت‌های نصب و انتشار](docs/INSTALLATION.md) انتشار npm و بررسی نصب از رجیستری
را جداگانه ثبت می‌کنند. پیش‌نمایش بدون امضای دسکتاپ برای macOS ARM64 و پیش‌نمایش
جدید IDE از همان هستهٔ JavaScript استفاده می‌کنند؛ پذیرش هر رابط جداگانه بررسی می‌شود.

### مشاهده‌شده با عامل‌های واقعی

[پذیرش ثبت‌شدهٔ CLI](docs/CORE_STATUS.md) شامل استفادهٔ اولیه و بازگشت به برنامه روی
Mac با Codex/ChatGPT و مدل محلی Qwen3 4B دانلودشده، تغییرهای مفید، ادغام پس از
بازبینی و ادامهٔ گفت‌وگو است. سابقهٔ Linux ARM64 Docker تعامل بومی، کار مفیدِ
بازبینی‌شده، ادغام و پاک‌سازی را ثبت می‌کند و timeout عامل نویسنده نیز حفظ شده است.
در Windows، کار مفید بومی، پیگیری در همان گفت‌وگو و ادغام صریحِ جداگانه ثبت شده‌اند.
کنترل‌های نهایی اتصال، خروج از اتصال، توقف و خروج CLI روی هر سه میزبان مشاهده شدند؛
سابقهٔ Mac از یک مشاهدهٔ ناقصِ تحویل ورودی که به مهلت کنترل‌گر رسید و یک مشاهدهٔ
جداگانهٔ توقف و خروج معمول تشکیل شده است.

این‌ها مشاهده‌های محدودِ وظیفه و چرخهٔ عمرند. شکست‌های قبلی در شواهد باقی مانده‌اند.
اجرای زندهٔ مدل با Claude، شاخه‌های شرطیِ اجرا‌نشدهٔ راه‌اندازی و بازیابی، کیفیت عمومی
کدنویسی و هزینهٔ واقعی ارائه‌دهنده اثبات نشده‌اند. برای محدوده و محدودیت‌های دقیق،
[شواهد فعلی](docs/CORE_STATUS.md) و [راهنمای پذیرش](docs/USER_ACCEPTANCE.md) را ببینید.

## شروع سریع

به **Node.js 22+ همراه npm** نیاز دارید. کار روی پروژه به Git در یک مسیر مطلقِ PATH
و یک مخزن Git تمیز و commit‌شده نیز نیاز دارد. کوتو می‌تواند کلاینت‌های بومی موجود
را پیدا کند یا نصب خصوصی و ورود بومی آن‌ها را پیشنهاد دهد. می‌توانید از اشتراک،
مدل محلی یا هر دو استفاده کنید؛ دانلود مدل محلی اختیاری است.

### 1. باز کردن کوتو

مسیر نصب نسخهٔ آلفا:

<div dir="ltr">

```sh
npm install --global @mehrdadz/koto@alpha
koto
```

</div>

بدون نصب سراسری:

<div dir="ltr">

```sh
npx --yes @mehrdadz/koto@alpha
```

</div>

برای انتخاب نسخهٔ دقیقِ پیش‌انتشار به‌جای دنبال‌کردن برچسب <code dir="ltr">alpha</code>:

<div dir="ltr">

```sh
npm install --global @mehrdadz/koto@3.0.0-alpha.1
koto
```

</div>

این فرمان‌ها توزیع آلفا را مشخص می‌کنند؛ انتشار و بررسی نصب از رجیستری، مرحله‌های
جداگانهٔ انتشارند که در [یادداشت‌های نصب](docs/INSTALLATION.md) ثبت می‌شوند.
هستهٔ Node وابستگی زمان اجرا، مرحلهٔ ساخت اجباری یا hook نصب ندارد.

<details>
<summary>اجرا از سورس یا نصب tarball محلی</summary>

مستقیماً از checkout اجرا کنید:

<div dir="ltr">

```sh
git clone https://github.com/mehrdadxzaker/Koto.git
cd Koto
node bin/koto.js
```

</div>

یا بسته را از همان checkout در محیط محلی بسازید و نصب کنید:

<div dir="ltr">

```sh
npm pack --ignore-scripts
npm install --global ./mehrdadz-koto-3.0.0-alpha.1.tgz
koto
```

</div>

برای استفادهٔ محلی از npm/npx، [راهنمای نصب](docs/INSTALLATION.md) را بخوانید.
اگر فرمان قدیمی Python با نام <code dir="ltr">koto</code> در PATH شما قرار دارد،
[راهنمای مهاجرت](docs/MIGRATION.md) را نیز ببینید.

</details>

### 2. انتخاب تنظیمات و پروژه

گفت‌وگوی اولین اجرا حساب‌های پشتیبانی‌شدهٔ Codex و Claude Code را شناسایی می‌کند.
ورود فعلی را انتخاب کنید، روند ورود بومی کلاینت را باز کنید یا در صورت نیاز نصب
خصوصی کلاینت را تأیید کنید. اطلاعات ورود نزد خود کلاینت می‌ماند؛ استفاده از اشتراک
به کلید API ارائه‌دهنده نیاز ندارد. شناسایی ورود، دسترسی به همهٔ مدل‌ها یا میزان
باقی‌ماندهٔ سهمیه را اثبات نمی‌کند.

راه‌اندازی اختیاری محلی، اندازهٔ مدل، مجوز و راهنمای حافظه را نمایش می‌دهد. پس از
تأیید شما، کوتو نسخهٔ مشخصی از runtime مربوط به llama.cpp را دریافت و صحت دانلود
مدل انتخابی را بررسی می‌کند. دارایی‌های تأییدشده در اجراهای بعدی دوباره استفاده
می‌شوند. کوتو هر بار یک سرور مدل محلیِ تحت مدیریت را اجرا و هنگام خروج متوقف می‌کند.
شروع سرور همچنان به بررسی حافظه و فضای ذخیره‌سازی فعلی وابسته است.

پوشهٔ پروژه را انتخاب کنید، با <code dir="ltr">new PATH</code> و پس از تأیید پروژه‌ای
بسازید یا برای ادامهٔ گفت‌وگو <code dir="ltr">later</code> را وارد کنید. کار روی پروژهٔ
موجود به مخزن تمیز و commit‌شده نیاز دارد. بعداً با <code dir="ltr">/project PATH</code>
یا <code dir="ltr">/new PATH</code> آن را عوض کنید.

**پیش‌نیازهای helper بومی:** نصب بسته هیچ helperی را کامپایل و هیچ کامپایلری را دانلود
نمی‌کند. helper میزبان به‌صورت صریح با ابزارهای نصب‌شده ساخته می‌شود و پیش از
استفاده صحت آن بررسی می‌شود:

| میزبان | پیش‌نیازهای ازقبل‌نصب‌شده | کاربرد helper |
| --- | --- | --- |
| macOS | ابزارهای توسعهٔ خط فرمان Apple و SDK | عامل‌های PTY |
| Linux | کامپایلر C سیستم، هدرهای توسعهٔ libc، procfs و مجازبودن فراخوانی‌های pidfd | عامل‌های PTY |
| Windows 10 1809 یا جدیدتر | ابزارهای C++ در Visual Studio و Windows SDK سازگار | همهٔ عامل‌های پروژه و بررسی اولیهٔ مخزن، از جمله حالت pipe |

گزینهٔ **Set up terminal support** در راه‌اندازِ راهنما همین ساخت را انجام می‌دهد.
با CLI نصب‌شده می‌توانید از این فرمان‌ها نیز استفاده کنید:

<div dir="ltr">

```sh
koto terminal build
koto terminal info
```

</div>

برای مسیرهای helper، تطبیق نسخه و نیازهای هر میزبان،
[راهنمای نصب](docs/INSTALLATION.md#build-the-host-helper) را ببینید. این سازوکارها
مالکیت فرایند را مدیریت می‌کنند و sandbox سیستم‌عامل ایجاد نمی‌کنند.

### 3. شرح، ویرایش و تأیید کار

پیامی بنویسید یا بگویید چه می‌خواهید بسازید. درخواست کدنویسی برنامه‌ای با عامل‌ها،
مدل‌ها، وظیفه‌ها و مسیر سهم هر عامل تولید می‌کند. برای تغییر وظیفه، انتخاب عامل یا
مدلِ تنظیم‌شده، مالکیت مسیرها، وابستگی‌ها یا حذف یک وظیفه، <code dir="ltr">edit</code>
را وارد کنید. کوتو برنامهٔ اصلاح‌شده را اعتبارسنجی و دوباره نمایش می‌دهد.
با <code dir="ltr">build</code> برنامهٔ بازبینی‌شده را از طریق هستهٔ مشترک اجرا کنید.

| هنگام نشست پروژه | عمل |
| --- | --- |
| <code dir="ltr">:status</code> | نمایش وضعیت عامل‌ها و worktreeها |
| <code dir="ltr">:attach AGENT</code> | ورود به ترمینال بومی؛ Ctrl-] به کوتو برمی‌گردد |
| <code dir="ltr">:resize AGENT 120 36</code> | تغییر اندازهٔ ترمینال بومی؛ ترمینال متصل از اندازهٔ ترمینال بیرونی نیز پیروی می‌کند |
| <code dir="ltr">:stop AGENT</code> / <code dir="ltr">:stop all</code> | توقف کار تحت مالکیت و حفظ ویرایش‌های ناقص |
| <code dir="ltr">:review AGENT</code> | نمایش و نگه‌داشتن بازبینیِ سهمی که ادغام بعدی اعمال می‌کند |
| <code dir="ltr">:integrate AGENT</code> | اعمال سهم نمایش‌داده‌شده پس از پایان همهٔ عامل‌ها و تأیید پاک‌سازی |
| <code dir="ltr">:quit</code> | توقف کار باقی‌مانده، حفظ نشست و بازگشت به گفت‌وگو یا راه‌انداز |

پرسش‌های مجوزِ ترمینال بومی را در ترمینال عامل موردنظر پاسخ دهید. کوتو مجوزها را
دور نمی‌زند. ادغام فقط در **worktree مستقلِ ادغام همان نشست** نوشته می‌شود و مستقیماً
شاخهٔ اصلی پروژهٔ شما را تغییر نمی‌دهد. سهم تغییریافته باید دوباره بازبینی شود.
تعارض‌ها برای حل دستی با Git و تأیید صریح باقی می‌مانند. نتیجهٔ ادغام را بازبینی و
برنامهٔ خود را اجرا کنید؛ سپس تصمیم بگیرید چگونه آن را وارد شاخهٔ معمول خود کنید.

### 4. بازگشت به کار ذخیره‌شده

دوباره <code dir="ltr">koto</code> را باز کنید تا انتخاب‌های حساب، پروژه، مدل و عامل‌ها
یادآوری شوند. <code dir="ltr">/sessions</code> کار ذخیره‌شده را انتخاب می‌کند؛
<code dir="ltr">/review</code>، <code dir="ltr">/integrate</code> و <code dir="ltr">/resume</code>
عامل را انتخاب و اقدام بعدی را راهنمایی می‌کنند؛ نیازی به کپی‌کردن مسیر پوشهٔ نشست نیست.
ادامهٔ پشتیبانی‌شده، همان گفت‌وگو و worktree اصلی را نگه می‌دارد. پس از ادغام، بازبینی
بعدی فقط تغییرهای بعدی را پوشش می‌دهد. نبود هویت بومی، تعارض حل‌نشده یا پاک‌سازیِ
تأییدنشده، ادامه یا ادغام را مسدود می‌کند.

با <code dir="ltr">/accounts</code>، <code dir="ltr">/agents</code>، <code dir="ltr">/models</code>
و <code dir="ltr">/help</code> انتخاب‌ها را ببینید. <code dir="ltr">/models add</code>
دریافت راهنمای مدل را باز می‌کند و <code dir="ltr">/models use MODEL_ID</code> یک مدل
دانلودشده را انتخاب می‌کند. برای کار روزمره و بازیابی،
[راهنمای نشست‌ها](docs/GUIDED_SESSIONS.md) را بخوانید. برای پروفایل‌های صریح
Codex/OpenCode، حالت‌های pipe و برنامه‌های اسکریپتی از <code dir="ltr">koto setup</code>
و [راهنمای نشست پروژه](docs/PROJECT_SESSIONS.md) استفاده کنید.
راه‌اندازی معمول به نوشتن دستی برنامهٔ JSON نیاز ندارد.

| --- | --- |
| انتقال ترمینال | pipe، PTY در macOS/Linux و ConPTY در Windows؛ پیش‌نیازهای helper برقرارند. صفحهٔ ترمینال بومی به‌عنوان هویت یا پایان ساخت‌یافته تفسیر نمی‌شود. |
| چرخهٔ عمر بومی | پروفایل‌های ساخت‌یافتهٔ پشتیبانی‌شدهٔ Codex/OpenCode شناسه و نتیجهٔ بومی را برای ادامهٔ صریح ثبت می‌کنند. قابلیت‌ها به adapter و حالت انتخابی وابسته‌اند. |
| مجوزها | سیاست مجوز کلاینت بومی حفظ می‌شود. مالکیت اعلام‌شده هنگام اجرا توصیه‌ای است؛ worktree یک sandbox سیستم‌عامل نیست. |
| نتیجه‌ها | خروج فرایند، پایان کار بومی و درستی کد جدا هستند. تغییرها همچنان به بازبینی و استفادهٔ واقعی از برنامه نیاز دارند. |
| لغو | پاک‌سازی فرایند یا نشستِ تحت مالکیت یا Job Object باید تأیید شود. <code dir="ltr">cleanup_unconfirmed</code> ادامه و ادغام را مسدود می‌کند. |
| بازیابی | بازاجرای خودکار وظیفه، تصمیم خودکار دربارهٔ تعارض یا حذف خودکار worktree وجود ندارد. نتیجهٔ مبهم ادغام به تطبیق صریح وضعیت نیاز دارد؛ کلاینت‌های بومی ممکن است تلاش مجدد خود را انجام دهند. |
| شواهد | CI سورس و helper، هویت بسته و نتیجهٔ واقعی وظیفه، شواهد جداگانه‌اند. محدودیت‌های مشاهده‌شدهٔ میزبان و کلاینت در اسناد پذیرش ثبت شده‌اند. |
| عرضه | CLI با نسخهٔ `3.0.0-alpha.1` منتشر شده است؛ دسکتاپ پیش‌نمایشی بدون امضا برای macOS ARM64 است. گردش کار پیش‌نمایش IDE در VS Code `1.144.0` و Cursor `3.27.22` روی macOS ARM64 مشاهده شد؛ میزبان‌های دیگر و انتشار Marketplace بررسی جداگانه دارند. |

انتخاب‌های خصوصی معمولاً در <code dir="ltr">~/.koto/preferences.json</code> نگه‌داری
می‌شوند؛ <code dir="ltr">KOTO_STATE_DIR</code> مسیر مطلق خصوصی دیگری را برای روند
راهنما انتخاب می‌کند. وضعیت نشست شامل پرامپت‌ها، خروجی بومی و مسیرهای فضای کاری است.
فایل‌های کنترل پیش‌فرض در <code dir="ltr">~/.koto/sessions</code> و worktreeها در
<code dir="ltr">~/.koto/sessions-worktrees</code> قرار دارند؛ مسیر صریح کنترل باید
خارج از worktreeهای پروژه باشد. حذف نصب کوتو این کارها را حذف نمی‌کند. اطلاعات ورود
و نشست‌های خصوصی را وارد commit یا گزارش issue نکنید.
[راهنمای امنیت](SECURITY.md) و
[محدودیت‌های نشست](docs/PROJECT_SESSIONS.md#boundaries-and-retained-data) را بخوانید.

## یک هسته، چند رابط

<div dir="ltr">

```js
import { createProjectSession } from '@mehrdadz/koto';

const session = await createProjectSession(plan, {
  onEvent: event => renderEvent(event)
});
const result = await session.run();
```

</div>

API مشترک شناسایی، ساخت و اصلاح برنامه، بررسی نشست ذخیره‌شده، ادامهٔ صریح، ادغام
با توکن تأیید و تطبیق وضعیت مبهم را نیز در اختیار می‌گذارد. گردش کارهای عمومی از
قرارداد ورودی JSON در stdin و خروجی متن در stdout استفاده می‌کنند؛ نشست‌های پروژه
فرمان‌های بومیِ اعلام‌شده در برنامهٔ خود را اجرا می‌کنند.

ترتیب توسعه **پذیرش روند CLI ← رابط‌های کاربری و افزونه‌های IDE با همان هسته** است.
هر رابط از همان عملیات و وضعیت محصول استفاده می‌کند. زمان‌بندی، مالکیت فضای کاری،
چرخهٔ عمر بومی و ادغام در هستهٔ مشترک باقی می‌مانند.
[معماری](docs/ARCHITECTURE.md)، [نقشهٔ راه](docs/ROADMAP.md) و
[محدودهٔ محصول](docs/SCOPE.md) را ببینید.
